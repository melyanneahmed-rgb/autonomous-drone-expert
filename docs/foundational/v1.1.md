## 1. Final Product Definition

منصة هندسية ذكية مستقلة لإعداد وتشخيص وبرمجة الدرونات بالكامل. المستخدم يعرّف المكونات التي
لا يمكن اكتشافها موثوقًا ويختار غرض الدرون وأسلوب الطيران؛ التطبيق يحوّل ذلك إلى إعداد كامل،
يبرمج الدرون فعليًا، يتحقق من كل تغيير، ويشخّص الأعطال كمهندس محقق. عائلات الفريموير
المدعومة هي محركات توافق داخلية وليست هوية المنتج ولا تظهر في واجهة الاستخدام العادية.

مبنية على طبقتين: **طبقة تنفيذية** تنفذ الدورة الذاتية الكاملة:

```
Discover -> Decide -> Plan -> Apply -> Reboot -> Verify -> Diagnose -> Recovery
```

و**طبقة ذكاء** من ثلاثة أعمدة معتمدة: Hardware Knowledge Database، Intelligent Diagnostic
Expert، Knowledge Engine.

النطاق النهائي الكامل (غير قابل للتقليص): محركات توافق داخلية متعددة، قراءة وبرمجة وflashing،
Receiver/GPS/VTX/ESC/Motors/Modes/Failsafe/Navigation، تشخيص، معرفة عتادية، تعلم متراكم،
Web/PWA أولًا على المتصفحات المتوافقة، ثم حزم Windows وAndroid من قاعدة المنتج نفسها، وبعدها
macOS وLinux حيث تسمح متطلبات العتاد.

## 2. Non-Negotiable Product Principles

1. **اقرأ قبل أن تسأل:** لا يُسأل المستخدم عن أي معلومة قابلة للاكتشاف الموثوق.
2. **قرارات تقنية صفر على المستخدم:** UART/baud/بروتوكولات/features/قيم — كلها مسؤولية
   المحركات؛ المستخدم يقدم أفعالًا فيزيائية وملاحظات وتأكيدات وهدفًا فقط.
3. **الإرسال ليس نجاحًا:** النجاح = قيمة معاد قراءتها + وظيفة تعمل + لا تدهور تراجعي
   (arming flags وقائمة الأجهزة العاملة قبل/بعد).
4. **لا حالة مجهولة صامتة:** كل جلسة تنتهي بإعداد متحقق، أو استعادة متحققة، أو حالة موثقة
   بإرشاد، أو إعلان صريح لحالة `STATE UNKNOWN — RECOVERY REQUIRED` — ولا يُدّعى نجاح لم يُثبت.
5. **صادق عند الحدود:** ما لا يمكن إثباته إلكترونيًا يُوسم (`REQUIRES HARDWARE TEST` /
   `MANUAL HARDWARE CHECK`) ولا يُدّعى؛ لا وعود زائفة.
6. **السلامة تنظم الأتمتة ولا تلغيها.**
7. **كل قرار قابل للتفسير:** ماذا/لماذا/الدليل/البدائل المرفوضة/التحقق/خطة الفشل.
8. **لا تخمين في العتاد أو السلامة.**
9. **عربية RTL أصيلة** وإنجليزية، بلا ترجمة آلية رديئة.
10. **Offline-first:** كامل الإعداد والتشخيص بلا إنترنت وبلا حساب.
11. **أتمتة الإعداد كاملة:** كل إعداد مدعوم وآمن يضبطه البرنامج تلقائيًا وفق المكونات وهدف
    الطيران؛ الاستثناء الوحيد للقرار التقني هو اختيار المستخدم اليدوي لوظيفة أزرار ومفاتيح
    جهاز التحكم.

| المستخدم | البرنامج |
| --- | --- |

| إعلان المكونات غير القابلة للاكتشاف (قائمة مصورة) | التحقق من كل مكوّن: مضبوط/موصول/يرسل/يستجيب/متحقق |

| حقائق فيزيائية قليلة: مراوح، خلايا، سعة، وزن، poles، بلد التشغيل — مع "لا أعرف" | كل القرارات التقنية عبر Solver + Decision Engine |
| حركات موجهة: عصي، مفاتيح، إمالات | اكتشاف القنوات والاتجاهات والتحقق من الحركة |
| تعيين يدوي لوظائف أزرار ومفاتيح جهاز التحكم | عرض المدخل الحي، حفظ اختيار المستخدم والتحقق منه دون اختراع الوظيفة بدلًا عنه |
| ملاحظات بصرية: سهم الدوران، ظهور OSD | تشغيل الاختبارات الآمنة وتفسير الملاحظات |
| تأكيدات السلامة وموافقات الخطر العالي | التنفيذ والحفظ والتحقق والتصحيح والاسترداد والتقرير |

## 4. Intelligence Authority Hierarchy (ملزم)

الأعلى يحكم الأدنى دائمًا:

1. Safety invariants.
2. Verified firmware and board capabilities.
3. Official specifications and defaults.
4. Live observed facts from the connected hardware.
5. User-confirmed physical facts.
6. Hardware Knowledge Database.
7. Verified community knowledge.
8. Statistical or learned insights.
9. Language-model suggestions.

المستويات 6–9 تستطيع: ترتيب الاحتمالات، تحسين اختيار اختبار التشخيص التالي، تقديم تحذير،
ترجيح بديل بين بدائل آمنة. ولا تستطيع منفردة: تشغيل محرك، تغيير failsafe أو arming، تنفيذ
flashing، تغيير firmware family، اختيار قيمة خارج النطاقات الرسمية والآمنة، أو تجاوز خطة
التحقق والاسترداد.

## 5. Autonomous Configuration Lifecycle

```
Connect -> Identify -> Read Snapshot -> Diagnose Build -> Ask (physical-only) -> Goal
-> Generate Plan -> Simulate -> Validate (compat/deps/safety) -> Declare Recovery Class
-> Approve -> Backup -> Apply (batched) -> Save -> Reboot -> Reconnect -> Re-identify
-> Re-read -> Verify -> Guided Tests -> Self-Correct (safe ladders)
-> Recovery on critical failure -> Readiness Report -> Record Case
```

أحكام ملزمة: دفعات مصممة بحيث تكون اللوحة متسقة وقابلة للإقلاع بعد كل save؛ checkpoints بين
الدفعات؛ منفذ الجلسة لا يُمس إلا بخطة إعادة اتصال مؤكدة؛ إعادة التعريف بعد كل reboot تطابق
الهوية (لوحة مختلفة → `Unsafe` وإلغاء)؛ MSP أولًا وCLI للفجوات؛ التصحيح الذاتي محدود
المحاولات، موثق، قابل للتراجع، ومحظور في نطاقات المحركات/arming/failsafe.

### Recovery Classes (ملزمة)

يُلغى مفهوم "rollback" العام. كل Change Plan وكل عملية كتابة أو flashing تعلن تصنيفها
**قبل التنفيذ**، ويُعرض للمستخدم ضمن الخطة:

| التصنيف | المعنى |
| --- | --- |
| `AUTOMATIC_ROLLBACK_SUPPORTED` | القيم السابقة قابلة لإعادة الكتابة آليًا والتحقق منها ضمن نفس الجلسة |
| `RESTORE_FROM_BACKUP_SUPPORTED` | الاسترداد يتطلب استعادة النسخة الاحتياطية المتوافقة عبر مسار الخطة/التحقق |
| `RECOVERY_REFLASH_REQUIRED` | لا استرداد إلا بإعادة فلاش الـ firmware ثم إعادة بناء الإعداد |
| `MANUAL_RECOVERY_REQUIRED` | يتطلب فعلًا فيزيائيًا موجهًا قبل أي استرداد برمجي |
| `ROLLBACK_NOT_GUARANTEED` | لا يمكن ضمان العودة للحالة السابقة — يتطلب موافقة صريحة منفصلة قبل التنفيذ |

### حالة تشغيلية مستقلة للكتابة المؤقتة

الكتابة المؤقتة في RAM (قبل تثبيتها في EEPROM) **لا توصف تلقائيًا بأنها rollback ناجح**.
تُستخدم لها حالة تشغيلية مستقلة:

```
TRANSIENT_WRITE_PENDING — RECONCILE_ON_RESUME
```

معناها: صدر أمر كتابة غير مثبّت؛ يجب التوفيق بينه وبين الواقع بإعادة قراءة عند استئناف
الجلسة أو بعد إعادة التشغيل، قبل أي ادعاء بنجاح أو بفشل.

### حالات الجاهزية الست

1. `READY — CONFIGURATION VERIFIED`
2. `READY — FLIGHT TEST REQUIRED`
3. `HARDWARE CHECK REQUIRED`
4. `NOT READY — CONFIGURATION FAILED`
5. `UNSUPPORTED HARDWARE`
6. `STATE UNKNOWN — RECOVERY REQUIRED`

تُستخدم السادسة عندما يتعذر إثبات حالة اللوحة أو إثبات نجاح الاستعادة؛ فيها لا يدّعي
البرنامج نجاحًا، ولا يعلن جاهزية طيران، ويقدم مسار استرداد موجهًا حسب التصنيف المعلن.

آلات الحالات الثلاث (Connection / Configuration / Safety) معتمدة؛ آلة السلامة تملك سلطة
المقاطعة المطلقة، وتضم `State Unknown` كحالة نهائية مانعة للطيران.

## 6. Diagnostic Expert Lifecycle

أساسه الملزم: deterministic diagnostic graphs، observable facts، capability data، safe
diagnostic tests، weighted hypotheses قابلة للتفسير، guided physical verification،
verified repair actions.

```
Symptom -> Free Evidence (snapshot + live) -> Hypotheses -> Rank
-> Cheapest Discriminating Test -> Narrow -> Repeat -> Conclusion + Confidence
-> Repair Plan -> Post-Repair Verification -> Fallback
```

كل تشخيص يعرض: العرَض، الأدلة، الفرضيات، سبب ترتيب كل فرضية، الاختبار التالي ولماذا،
المستبعَد، النتيجة ودرجة الثقة، الإصلاح، التحقق بعده، والبديل عند الفشل.

**قاعدة الثقة الملزمة:** لا نسب رقمية قبل توفر نموذج معاير وبيانات كافية — تُستخدم التصنيفات
`Very likely` / `Likely` / `Possible` / `Uncertain` مع شرح الأدلة.

التغطية: GPS، Receiver، ESC، Motors، OSD، VTX، USB، DFU، Arming، Failsafe، GPS Rescue،
Position Hold، RTH، Blackbox، Telemetry. الخبير لا يملك صلاحية كتابة خاصة: كل إصلاح يمر
بمسار الخطة/السلامة/التحقق نفسه ويعلن تصنيف استرداده.

## 7. Hardware Knowledge Data Model

موسوعة عتاد versioned موقعة، منفصلة عن الكود، تُحدّث كحزم بيانات. الفئات: FC، ESC، Motor،
Receiver، GPS، VTX/VRX، Camera، Frame، Battery.

**تصنيف المصدر الإلزامي:** `OFFICIAL_MANUFACTURER_DATA` / `UPSTREAM_FIRMWARE_DATA` /
`PROGRAM_OBSERVED_DATA` / `HARDWARE_TEST_VERIFIED` / `COMMUNITY_REPORTED` /
`STATISTICALLY_INFERRED` / `UNVERIFIED`.

**حقول كل سجل الإلزامية:** المصدر، تاريخ القراءة/التحقق، إصدار الوثيقة، نطاق إصدارات الـ
firmware، مستوى الثقة، الاستخدام (قرار أم تحذير فقط)، مرجع provenance داخلي، حالة الترخيص.

**قيد ملزم:** لا تُضمّن target definitions أو presets أو جداول من مستودعات GPL قبل تحليل
أثر التضمين أو الاشتقاق على ترخيص المشروع ومراجعته قانونيًا. القطع المجهولة لا تعطل شيئًا:
الموسوعة تحسّن القرار ولا تشترطه.

## 8. Knowledge Engine Governance

**لا تعلم مباشر داخل الإنتاج:**

```
Case Recording -> Validation -> Aggregation -> Insight Candidate -> Review
-> Test Suite -> Signed Knowledge Pack -> Production Use
```

كل insight يحمل إلزاميًا: حجم العينة، توزيع إصدارات الـ firmware، أنواع اللوحات، نسبة
النجاح، نسبة الفشل، مستوى الثقة، العوامل المربكة المحتملة، الاختبارات المجتازة، تاريخ
الإصدار، وقابلية التعطيل/الرجوع لنسخة أقدم. أي insight غير موقع أو غير مختبر لا يدخل قرارًا
إنتاجيًا.

**بيانات وصفية إلزامية لكل Knowledge Pack:** schema version، minimum compatible app
version، review/expiry date، revocation identifier، rollback version، signing key ID.
حزمة منتهية الصلاحية أو مُبطلة أو غير متوافقة لا تُستخدم في أي قرار، ويعود النظام تلقائيًا
إلى rollback version المعلنة.

مبادئ الاستخلاص: إحصاء قابل للتفسير قبل أي تعلم آلي؛ عتبات عينة ودلالة؛ الارتباط ليس سببية؛
فصل صارم حسب firmware family/version؛ خضوع كامل لهرمية السلطة.

## 9. Privacy and Community Contribution Policy

**النسخة الأولى (ملزم):** Offline-first؛ كل الحالات محلية فقط؛ لا رفع تلقائي، لا حساب، لا
telemetry؛ الحالات لا تتضمن: serial numbers، USB UID، إحداثيات GPS، home position، أسماء
شبكات، أو أي معرف/hash ثابت يسمح بتتبع الدرون عبر الجلسات.

**عند تنفيذ المشاركة لاحقًا:** opt-in صريح؛ عرض المحتوى كاملًا قبل الإرسال؛ حق حذف الحقول؛
معرفات جلسة مؤقتة؛ تعميم/حذف التركيبات النادرة؛ سياسة حذف واحتفاظ معلنة؛ عدم تأثير المشاركة
أو رفضها في أي وظيفة أساسية.

**موسوعة العتاد:** `Internal Editorial Model First` — تحرير داخلي بمراجعة ومصدر لكل سجل؛ لا
إدخال مجتمعي مباشر للإنتاج؛ المساهمات لاحقًا إلى staging ولا تُنشر قبل المراجعة والاختبارات.

## 10. Safety and Write-Authority Model

- **تصنيف كل أمر إلزامي في الكود:** transient MSP / persistent write / CLI set / save
  (EEPROM+reboot) / bootloader reboot / DFU flash / full erase / defaults reset / restore —
  الـ Executor يرفض أمرًا بلا تصنيف، **وبلا Recovery Class معلن**.
- **مصفوفة سلطة الكتابة:** خطر منخفض → تلقائي ضمن خطة موافق عليها؛ متوسط → تأكيد سياقي؛ فعل
  فيزيائي → إرشاد ثم تنفيذ؛ عالٍ (motors/flashing/family change/restore) → بوابة منفصلة
  صريحة؛ أي عملية `ROLLBACK_NOT_GUARANTEED` → موافقة صريحة منفصلة مهما كان خطرها الظاهري.
- **بوابة المحركات الكاملة:** تأكيد مزدوج لإزالة المراوح، تثبيت ومساحة آمنة، throttle منخفض
  مقروءًا حيًا، منع arming، موافقة لكل محرك، E-stop دائم، timeout، إيقاف فوري عند فقدان
  الاتصال، لا حفظ لنتيجة غير مؤكدة، ولا تدوير تلقائي أبدًا.
- **محظورات flashing:** لا فلاش بـ target غير مؤكد؛ لا تغيير family بلا موافقة صريحة منفصلة؛
  لا استعادة backup غير متوافق؛ backup إجباري قبل الـ bootloader.
- **الكتابة على عتاد حقيقي:** محظورة حتى نجاح الدورة كاملة على Mock وReplay ثم موافقة منفصلة
  على بوابة Hardware Write.
- الطبقة الحوارية والمعرفة المتعلمة: بلا أي مسار كتابة مباشر.

## 11. Technical Architecture

**المنصة (معتمدة):** واجهة TypeScript/React عربية RTL-first تعمل كـ Web/PWA، مع Rust core
حتمي قابل للبناء لـ WebAssembly وللمنصات الأصلية. الاتصال في الويب يمر عبر Web Serial خلف
واجهة Transport غير متزامنة؛ التخزين المحلي يمر عبر Storage interface (IndexedDB في الويب
وتخزين crash-safe أصلي في الحزم). Tauri أو غلاف أصلي آخر طبقة تغليف اختيارية لوظائف لا
يسمح بها المتصفح، وليس هوية المنتج. التفاصيل في ADR-0010.

**قيد ملزم:** طبقات Serial/USB/DFU خلف interfaces مستقلة قابلة للاستبدال؛ كل مكتبة تمر بـ
Dependency Audit منفصل قبل الإدخال؛ لا plugin غير رسمي لمجرد توفره.

**الطبقات:**

1. **Transport:** Serial، USB enumeration/hotplug، DFU — خلف `Transport` interface.
2. **Protocol:** MSP codec (v1/v2/v2-over-v1/jumbo/CRC)، MSP Session Manager، CLI Session
   Manager.
3. **Intelligence Platform:** Hardware Knowledge DB، Rules & Presets DB، Knowledge Engine،
   Diagnostic Expert، Knowledge Distribution Service (معماريًا الآن، تنفيذًا لاحقًا).
4. **Core Engines:** Firmware Detector + BF/INAV Capability Adapters، Discovery Engine،
   Safe Probe Engine، Facts & Confidence Store، Dynamic Assessment، Decision Engine،
   Constraint Solver، Goal-to-Configuration + Simulation، Plan Generator (يعلن Recovery
   Class لكل بند ومجموعة)، Safety Validator.
5. **Execution:** Change Executor، Reconnect Manager، Post-Apply Verifier، Self-Correction
   Engine، Backup/Restore، Recovery Manager، Flashing Engine، Audit Log، Diagnostic Export.
6. **Presentation:** Web/PWA أولًا ثم أغلفة Windows/Android → أوامر معرفة فقط → UI +
   Localization + Guided Test Orchestrator. الواجهة لا ترى MSP ولا CLI ولا أسماء محركات
   التوافق الداخلية إطلاقًا.
7. **Test Infrastructure:** Mock FC، Replay System، Fault Injection Harness، Hardware Test
   Harness.
8. **عقود الطبقة الحوارية (تصميم الآن، تنفيذ لاحقًا):** كل المحركات تُخرج Structured
   Outputs؛ أي إجراء يُنتج أولًا كـ Structured Action ويمر عبر Safety Validator وPlan
   Executor؛ النموذج اللغوي بلا وصول لـ MSP/CLI/flashing/motors؛ ليس شرطًا لعمل أي وظيفة.

## 14. First Vertical Implementation Slice

**الهدف:** `Automatic Beeper Configuration and Verification on One Exact Betaflight Target
and Version` — لوحة واحدة محددة بالاسم وإصدار firmware واحد محدد بالضبط.

**الدورة الإلزامية:** Identify → Read → Plan (مع إعلان Recovery Class) → Backup → Write →
Save → Reboot → Reconnect → Verify → **Injected Failure** → Restore/Recovery → Final Report
→ Local Case Record.

**Basic OSD** هو الشريحة الرأسية الثانية بعد إثبات النواة على Beeper.

**معايير التعريف (بدل معيار زمن ثابت):** median وp95 يُقاسان ويُوثقان بعد التنفيذ؛ timeout
قابل للضبط؛ واجهة غير متجمدة وقابلة للإلغاء؛ تشخيص صريح لحالات port busy / permission
denied / driver missing؛ **zero write commands أثناء التعريف** مؤكَّدًا باختبار؛ audit لكل
outbound frame؛ وعدم فتح منافذ عشوائية دون اختيار المستخدم أو مطابقة معرّف موثوقة.

## 15. Acceptance Criteria

**لكل مرحلة:** (أ) الدورة الكاملة تعمل على Mock/Replay بكل سيناريوهات الفشل بما فيها الفشل
المحقون والاسترداد وإعلان `STATE UNKNOWN` عند تعذر الإثبات؛ (ب) موافقة Hardware Write ثم
إثبات على عتاد المختبر؛ (ج) كل قدرة معلنة إما `VERIFIED` آليًا أو موسومة بصنفها الصادق؛
(د) لا انحدار في اختبارات المراحل السابقة؛ (هـ) سجل provenance مكتمل لأي إضافة بروتوكولية؛
(و) تقرير مرحلة يُعرض على المالك قبل فتح المرحلة التالية.

**معايير هندسية إلزامية في كل مرحلة:** property-based tests؛ fuzzing لكل parser؛
deterministic timeout tests بزمن محقون؛ branch coverage للمسارات الحرجة (التنفيذ، التحقق،
الاسترداد، السلامة)؛ **no unreviewed unsafe Rust**؛ outbound-command audit assertions؛
crash-safe local case recording؛ power-loss وprocess-kill recovery tests.

**للمنتج النهائي (M12):**

> A beginner can take a supported build listed in the Hardware Support Matrix from
> connection to READY by declaring non-discoverable components, choosing a flight intent,
> manually assigning control switch/button functions, and performing only guided physical
> actions and safety confirmations. Every other supported configuration decision is made,
> applied and verified by the program.

إضافة إلى: محترف يجد التفسير الكامل والسجل والوضع المتقدم؛ كل حالات الجاهزية الست قابلة
للوصول ومختبرة؛ الخبير التشخيصي يغطي المجالات الخمسة عشر؛ إصدارات موقعة بثلاث منصات.
